# Архітектура бота «Для рішучих»

Документ фіксує рішення, ухвалені **до** початку розробки: архітектуру, технології, базу даних і хостинг.
Якщо рішення змінюється — спочатку оновлюємо цей файл, потім код.

---

## 1. Вимоги і як вони закриваються

| Вимога з ТЗ | Рішення |
|---|---|
| `/start` фіксує час першого запуску і запускає персональний таймер на 24 год | Під час першого `/start` у таблицю `users` записуються `started_at` і `deadline_at = started_at + offer_duration`. Запис робиться один раз (`INSERT … ON CONFLICT DO NOTHING`) |
| Повторний `/start` не перезапускає таймер | `started_at`/`deadline_at` ніколи не перезаписуються. Повторний `/start` просто надсилає офер ще раз із поточним залишком часу |
| Офер + таймер + текст «Пропозиція для рішучих. Діє 24 години» + кнопка «Обрати пакет» | Шаблон `messages.offer` з підстановкою `{timer}`, кнопки з `keyboards.offer`. Таймер «живий»: відлік «23:59:55» і смужка залишку часу; бот редагує повідомлення з таймером кожні 5 с, поки людина в чаті, інакше раз на хвилину |
| Список пакетів із назвою і ціною → розширений опис | Пакети з `packages` у `content.yaml`. Кнопки списку `{name} — {price}`. Після вибору надсилається `description` пакета |
| Під описом: «Отримати посилання на оплату», «Подивитися інші пакети» | `keyboards.package` (порядок і розміщення редагуються) |
| Надіслати платіжне посилання пакета, без перевірки оплати | `messages.payment` + кнопка-посилання `pay_url`. Оплата не перевіряється, доступ видає менеджер вручну (за бажанням бот повідомляє менеджера про запит посилання) |
| Нагадування протягом 24 год із залишком часу, розклад і тексти в конфігурації | `reminders` у `content.yaml` (`after` — від старту, `before_end` — до кінця). Надсилає фоновий планувальник |
| Після 24 год нагадування припиняються, бонусна пропозиція недійсна | Планувальник надсилає лише до `deadline_at`. Після дедлайну офер редагується («час вийшов», кнопки прибираються), кнопки зі старих повідомлень відповідають текстом `messages.expired` |
| Увесь контент в окремому файлі | `content.yaml`: тексти, пакети, ціни, описи, посилання, нагадування, назви і порядок кнопок |
| Робота 24/7, збереження даних, таймер після перезапуску | Хмарний хостинг Railway + постійний диск (Volume) + SQLite. Увесь стан у БД, у пам'яті нічого критичного |

## 2. Технології

| Складова | Вибір | Чому |
|---|---|---|
| Мова | **Python 3.12+** (тести проганяються на 3.13) | Найпоширеніша мова для Telegram-ботів, простий запуск на Windows і на хостингу |
| Telegram-фреймворк | **aiogram 3** | Зрілий асинхронний фреймворк з повною підтримкою Bot API, інлайн-кнопок і обробки помилок |
| Отримання оновлень | **long polling** | Не потрібні домен, HTTPS-сертифікат і вебхук; працює на будь-якому хостингу. Telegram зберігає оновлення до 24 год, тож під час перезапуску нічого не губиться |
| База даних | **SQLite** (через `aiosqlite`), режим WAL | Один файл, окремий сервер БД не потрібен; для тисяч користувачів цього з запасом достатньо; резервна копія — копія одного файлу |
| Контент | **YAML** (`content.yaml`) | Підтримує коментарі й багаторядкові тексти, зручно редагувати навіть у веб-редакторі GitHub |
| Час | `zoneinfo` + пакет `tzdata` | Коректний київський час, включно з переходом на літній/зимовий; на Windows без `tzdata` часових поясів немає |
| Тести | `pytest` + `pytest-asyncio`, фейковий Telegram | Перевірка всіх сценаріїв без мережі, без токена і без очікування 24 годин (керований час) |
| Збірка | **Docker** (`python:3.13-slim`) | Однакова збірка на Railway і на VPS. Під час збірки перевіряється `content.yaml`: з помилкою в контенті нова версія не збереться, а стара продовжить працювати |
| Хостинг | **Railway** (план Hobby) + **Volume** | Деплой із GitHub у кілька кліків, автоперезапуск, постійний диск. Альтернатива — будь-який VPS з Docker |

### Чому не інші варіанти
* **Вебхук замість polling** — потрібен публічний HTTPS-домен. Для одного бота з помірним навантаженням це лише ускладнює налаштування.
* **PostgreSQL** — окремий платний сервіс і більше налаштувань. SQLite на постійному диску закриває вимоги. Робота з БД зібрана в одному модулі (`bot/storage.py`), тож за потреби перехід на PostgreSQL зачепить лише його.
* **Безкоштовні тарифи Render/Koyeb тощо** — «засинають» без вхідного трафіку та/або не мають постійного диска. Для бота з таймерами це неприйнятно.

## 3. Хостинг і збереження даних

* **Railway**, один сервіс, збірка з `Dockerfile` з цієї папки.
* **Volume** (постійний диск) змонтований у `/data`. Railway сам передає змінну `RAILWAY_VOLUME_MOUNT_PATH`, тож бот автоматично зберігає базу в `/data/bot.db`. Якщо бот бачить, що працює на Railway **без** Volume, він пише в лог помітне попередження (без диска дані зникнуть при наступному деплої).
* Railway не запускає дві копії сервісу з Volume одночасно: під час деплою стара копія зупиняється до старту нової. Короткий простій (десятки секунд) не страшний: Telegram притримує повідомлення, а планувальник після старту доганяє пропущене.
* Вартість: план Hobby — $5/міс, з них $5 — кредит на ресурси; такий бот зазвичай у нього вкладається. Новим акаунтам дають пробний період ($5 разово, 30 днів), цього вистачить, щоб усе перевірити.
* Альтернатива: VPS (Hetzner, DigitalOcean чи будь-який український провайдер) + `docker compose` з іменованим томом. Інструкція — `DEPLOY.md`, варіант Б.
* Для перевірки — запуск на Windows подвійним кліком `start_bot.bat`: середовище Python і база лежать у `%LOCALAPPDATA%\TgBotDlyaRishuchih`, поза OneDrive (OneDrive не синхронізує тисячі файлів середовища і не блокує файл бази під час запису).
* Railway більше не приймає нові сервіси з `railway.toml` (Config as Code застарів, жорстка дата відключення — 01.12.2026). Тому налаштування сервісу задаються в панелі Railway, а збірка повністю описана в `Dockerfile`.

## 4. Компоненти

```
               ┌──────────────── процес бота (python -m bot) ─────────────────┐
 Telegram  ⇄   │  aiogram (polling) ──► handlers.py ──► funnel.py ──┬─► texts.py    (тексти і кнопки з content.yaml)
 Bot API       │                                         ▲          ├─► storage.py  (SQLite: users, reminder_log, events)
               │  scheduler.py (фонові цикли, ~15 с) ────┘          └─► sender.py   (надсилання/редагування з обробкою помилок)
               └───────────────────────────────────────────────────────────────┘
```

| Модуль | Відповідальність |
|---|---|
| `bot/config.py` | Змінні середовища: токен, шлях до БД (з авто-визначенням Volume на Railway), менеджер, адміністратори |
| `bot/content.py` | Завантаження і перевірка `content.yaml` → незмінні об'єкти `Content`, `Package`, `Reminder`. Зрозумілі повідомлення про помилки українською |
| `bot/timeutils.py` | Розбір тривалостей (`24 год`, `90 хв`, `1h30m`), формат `{time_left}` і `{deadline}`, «тихі години», годинник (`Clock`) |
| `bot/htmltext.py` | Перевірка Telegram-HTML у текстах, екранування, підстановки `{...}` |
| `bot/texts.py` | Формування всіх текстів і клавіатур для конкретного користувача в конкретний момент |
| `bot/storage.py` | SQLite: схема, міграції, всі запити |
| `bot/sender.py` | Безпечні виклики Telegram API: flood control, заблоковані користувачі, «повідомлення не змінено», запасний варіант без HTML, обмеження швидкості для фонових розсилок |
| `bot/funnel.py` | Бізнес-логіка воронки: старт, пакети, опис, оплата, нагадування, завершення, сповіщення менеджера |
| `bot/handlers.py` | Маршрутизація апдейтів aiogram до `funnel.py` |
| `bot/scheduler.py` | Фонові цикли: нагадування, завершення пропозиції, оновлення живого таймера |
| `bot/app.py`, `bot/__main__.py` | Збирання всього разом, запуск, коректна зупинка |
| `bot/check_content.py` | `python -m bot.check_content` — перевірка `content.yaml` без запуску бота |

## 5. Дані (SQLite)

Усі часові мітки — UTC, цілі unix-секунди.

**`users`** — один рядок на користувача
| Поле | Опис |
|---|---|
| `user_id` (PK), `chat_id` | Telegram id |
| `first_name`, `last_name`, `username`, `language_code` | Профіль (оновлюється при кожній взаємодії) |
| `source` | Параметр глибокого посилання з першого `/start` (`t.me/bot?start=instagram`), для аналітики |
| `started_at`, `deadline_at` | Перший `/start` і кінець пропозиції. **Записуються один раз** |
| `offer_message_id` | Повідомлення з живим таймером (його редагує планувальник) |
| `offer_body_message_id` | Текст оферу, якщо таймер — окремим повідомленням (`messages.offer_timer`); схема v2 |
| `expiry_done` | Завершення вже оброблено (офер відредаговано, повідомлення надіслано) |
| `blocked_at` | Користувач заблокував бота (знімається при наступній взаємодії) |
| `last_seen_at` | Остання взаємодія |

**`reminder_log`** — `(user_id, reminder_id)` PK, `status` (`sent` / `skipped` / `failed`), `at`. Гарантує, що кожне нагадування надходить не більше одного разу.

**`events`** — журнал дій (`start`, `restart`, `packages`, `package`, `payment_link`, `reminder`) для статистики `/stats`.

Версія схеми — `PRAGMA user_version`, міграції застосовуються автоматично під час запуску.

## 6. Ключові сценарії

**Перший `/start`**: створити користувача (`started_at = now`, `deadline_at = now + 24 год`) → надіслати офер → запам'ятати `offer_message_id`.
Якщо задано `messages.offer_timer`, офер — двома повідомленнями: текст (ніколи не редагується, тож «шторки» `<blockquote expandable>` і спойлери в ньому не згортаються) і коротке повідомлення з живим таймером і кнопкою «Обрати пакет». Інакше — одне повідомлення з `{timer}`.

**Повторний `/start`**, пропозиція діє: оновити профіль, **не чіпати** таймер → надіслати офер заново з поточним залишком → попереднє повідомлення з офером видалити, щоб у чаті був один живий таймер.

**Повторний `/start` після дедлайну**: надіслати `messages.expired`.

**«Обрати пакет» / «Подивитися інші пакети»** → список пакетів (кнопки «назва — ціна»).
**Пакет** → розширений опис + кнопки з `keyboards.package`.
**«Отримати посилання на оплату»** → `messages.payment` з посиланням + кнопка «Перейти до оплати»; подія `payment_link`; за наявності `MANAGER_CHAT_ID` — сповіщення менеджеру.

Після дедлайну будь-яка кнопка відповідає `messages.expired`. Якщо в `content.yaml` увімкнено `packages_after_expiry: true`, пакети лишаються доступними (за звичайною ціною і посиланням, якщо вони вказані).

## 7. Таймер і нагадування

* Дедлайн фіксується в момент першого `/start`. Якщо потім змінити `offer_duration` у `content.yaml`, нове значення діятиме лише для нових користувачів.
* **Планувальник** працює у двох фонових циклах (крок ~15 с). Кожен прохід читає стан із БД, тож перезапуск сервера нічого не ламає:
  1. **Нагадування.** Для кожного користувача з активною пропозицією обчислюються нагадування, час яких настав, але яких ще немає в `reminder_log`. Надсилається **лише найсвіжіше**, старіші позначаються `skipped`: після простою сервера людина не отримає пачку нагадувань одразу. Час нагадування: `started_at + after` або `deadline_at − before_end`.
  2. **Завершення.** У кого дедлайн минув і `expiry_done = 0`: офер редагується (рядок таймера → `timer_expired`, кнопки прибираються, якщо пакети після дедлайну недоступні), за бажанням надсилається `messages.expired_notice` (не пізніше ніж через 2 год після дедлайну, щоб після довгого простою не надсилати застарілих повідомлень).
  3. **Живий таймер** (окремий цикл; зі швидким відліком — щосекунди). Повідомлення з таймером редагується, коли змінилося показане значення:
     поки людина активна в чаті (`last_seen_at` — /start, кнопка, повідомлення — не давніше за `timer_fast_for`), не частіше `timer_fast_every` (5 с), інакше — не частіше `timer_update_every` (1 хв).
     `{countdown}` округлюється вгору до кроку оновлення (крок 5 с → «23:59:55», «23:59:50»; хвилина → цілі хвилини), тож відлік рівний і лише зменшується.
     Якщо Telegram просить зачекати (flood control), таймер цього чату ставиться на паузу на вказаний час, а решта таймерів оновлюється далі — планувальник не чекає.
     Фонові запити обмежені ~20/с, щоб не впертися в ліміти Telegram.
* **«Тихі години»** (`silent_hours`, за замовчуванням 22:00–08:00 за київським часом): нагадування приходять без звуку, але вчасно.

## 8. Обробка помилок

| Ситуація | Поведінка |
|---|---|
| Користувач заблокував бота | `blocked_at`, нагадування і таймер для нього зупиняються. Знімається, щойно людина знову натисне `/start` або кнопку |
| Flood control (429) | Пауза `retry_after` і повтор |
| Помилка HTML-розмітки | Повтор без форматування: повідомлення все одно доходить, у лозі попередження |
| Мережа / 5xx | Кілька повторів із паузою. Нагадування, яке не вдалося надіслати, повториться на наступному проході |
| Повідомлення з офером видалене | `offer_message_id` очищається, таймер для нього більше не оновлюється |
| Невірний токен | Бот завершується з зрозумілим повідомленням у лозі |
| Помилки в `content.yaml` | Бот не стартує, а на хостингу не збирається. У лозі — список помилок з назвами полів українською |
| Telegram недоступний під час старту | Бот чекає і пробує знову (не падає) |

## 9. Налаштування

* **`content.yaml`** — усе, що бачить користувач, плюс розклад (тривалість пропозиції, нагадування, тихі години, частота оновлення таймера).
* **Змінні середовища** — секрети і технічні параметри:

| Змінна | Обов'язкова | Опис |
|---|---|---|
| `BOT_TOKEN` | так | Токен від @BotFather |
| `MANAGER_CHAT_ID` | ні | Куди надсилати сповіщення про запити посилань на оплату |
| `ADMIN_IDS` | ні | Id адміністраторів через кому (команда `/stats`) |
| `DB_PATH` | ні | Шлях до файлу БД. За замовчуванням `$RAILWAY_VOLUME_MOUNT_PATH/bot.db` на Railway або `data/bot.db` локально |
| `CONTENT_PATH` | ні | Інший файл контенту (за замовчуванням `content.yaml`) |
| `LOG_LEVEL` | ні | `INFO` (за замовчуванням) або `DEBUG` |
| `TELEGRAM_API_URL` | ні | Власний сервер Bot API (для тестів) |
| `SCHEDULER_TICK_SECONDS` | ні | Крок планувальника, за замовчуванням 15 (для тестів) |

## 10. Безпека і дані

* Токен — лише у змінних середовища (`.env` локально, Variables на Railway). `.env` у `.gitignore`.
* Бот не обробляє платіжних даних: лише надсилає посилання.
* Зберігаються мінімальні дані: Telegram id, ім'я, username, мова, час старту і дії в боті.

---

## 11. Обмеження і масштаб

* Telegram дозволяє близько 30 повідомлень на секунду (і ~1 на секунду в одному чаті). Живий таймер — одне редагування на хвилину на кожного користувача з активною пропозицією, а швидкий відлік (раз на 5 с) — лише для тих, хто щось робив у чаті за останні 15 хв (зазвичай одиниці). Це комфортно до ~1000 одночасно активних пропозицій. За більшої кількості таймер просто оновлюватиметься рідше: обмежувач швидкості це враховує.
* Частіше ніж раз на 3 с таймер не оновлюється (перевірка `content.yaml`): у тому самому чаті боту ще треба відповідати на натискання кнопок.
* Polling дозволяє лише **один** запущений екземпляр бота з тим самим токеном. Локальні тести — з окремим тестовим ботом.

## 12. Тестування

* Тести працюють на власному еталонному контенті `tests/fixtures/content.yaml`, тож зміни тексту замовником їх не ламають; щодо справжнього `content.yaml` перевіряється лише його коректність.
* Юніт-тести: тривалості, формати часу, HTML, підстановки, валідація контенту, БД.
* Сценарні тести через справжній диспетчер aiogram із фейковою HTTP-сесією: `/start`, повторний `/start`, пакети, опис, оплата, дедлайн, сповіщення менеджера.
* Планувальник — з керованим годинником: нагадування в потрібний час, без дублів, після «перезапуску» (нове з'єднання з тим самим файлом БД), завершення пропозиції.
* E2E-скрипт `scripts/e2e_restart_check.py`: справжній процес бота проти локального фейкового Bot API, з реальною зупинкою і повторним запуском процесу. З `--docker IMAGE` — те саме для Docker-образу в умовах, як на Railway (Volume у `/data`, кожен перезапуск — новий контейнер).
