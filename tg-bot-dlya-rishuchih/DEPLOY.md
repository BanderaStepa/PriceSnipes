# Розміщення бота на хостингу — покрокова інструкція

Після цих кроків бот працює **цілодобово на хмарному сервері**, незалежно від вашого комп'ютера.
Дані (хто й коли натиснув `/start`, які нагадування вже надіслано) лежать на **постійному диску**,
тож після перезапуску сервера чи оновлення бота таймери продовжують іти з того самого місця.

* **Варіант А — Railway** (рекомендую): усе мишкою в браузері, ≈ 30 хв, ≈ $5 на місяць.
* **Варіант Б — власний сервер (VPS) з Docker**: дешевше (≈ €4–6/міс), але потрібна командна строка.

> Назви кнопок у панелі Railway можуть трохи відрізнятися — Railway часто оновлює інтерфейс.
> Інструкцію звірено з документацією Railway станом на листопад 2026 року.

## Як розміщено зараз (з 9 листопада 2026)

Бот **уже працює цілодобово на Railway**. Усе налаштував Claude через API Railway; від замовника знадобився лише
токен Railway (введено в захищену форму, у файлах і чатах його немає). Кроки варіанта А нижче — для довідки
або якщо колись знадобиться налаштувати все з нуля.

| Що | Значення |
|---|---|
| Проєкт / сервіс | `dlya-rishuchih-bot` / `bot` (railway.com → Dashboard) |
| Регіон | EU West (Амстердам) — поруч із серверами Telegram, кнопки відповідають швидше |
| Постійний диск | Volume `/data`, база `/data/bot.db` (бот знаходить її сам) |
| Налаштування | Restart Policy: **Always**, без сну (Serverless вимкнено), 1 копія, публічний домен не потрібен |
| Змінні | `BOT_TOKEN`, `ADMIN_IDS` (доступ до `/stats` і `/preview`) |
| Код | заливається скриптом `scripts/railway_deploy.py`, а не з GitHub: зміни на GitHub самі не розгортаються |

Базу з користувачами перенесли з хмарної сесії без втрат: таймери, дедлайни й надіслані нагадування збережено.

**Оновити бота** (тексти, ціни, кнопки): напишіть Claude, що змінити, — він змінить `content.yaml`, перевірить
і заллє. Технічно: commit → з папки бота `python scripts/railway_deploy.py` → скрипт чекає на запуск і показує
журнал. Якщо в `content.yaml` помилка, нова версія не збереться, а попередня працюватиме далі.
На власному комп'ютері скрипт теж працює: потрібні git і змінна `RAILWAY_API_TOKEN`
(railway.com/account/tokens → **Create Token**, Workspace: **No workspace**).

**Журнал і стан:** `python scripts/railway_deploy.py --logs 100` і `--status`, або в панелі Railway:
сервіс `bot` → **Deployments** → **View logs**.

**Змінити токен бота** (після `/revoke` у @BotFather): Railway → `dlya-rishuchih-bot` → `bot` → **Variables** →
`BOT_TOKEN` → вставте новий токен → **Deploy**. Нікуди більше його не надсилайте.

⚠️ **Не запускайте бота ще десь** (`start_bot.bat`, docker, інший хостинг) з тим самим токеном, поки він працює
на Railway: Telegram віддає повідомлення лише одній копії, а нагадування й таймери почнуть дублюватися.

## Варіант А — Railway

### Крок 1. Створіть бота і отримайте токен

1. У Telegram відкрийте **@BotFather** → **Start**.
2. Надішліть `/newbot`.
3. Введіть назву, яку бачитимуть люди, наприклад `Для рішучих`.
4. Введіть username латиницею, що закінчується на `bot`, наприклад `dlya_rishuchyh_bot`.
5. BotFather надішле **токен** виду `123456789:AAH…` — збережіть його.

> ⚠️ Токен — це пароль від бота. Не надсилайте його в чати, не публікуйте і не кладіть у файли на GitHub.
> Якщо токен «засвітився» — у @BotFather: `/revoke` → виберіть бота → отримаєте новий.

Необов'язково, але бажано: у @BotFather `/setdescription` (текст, який людина бачить до натискання Start),
`/setabouttext`, `/setuserpic` (аватар бота).

Найпростіше — через сайт:

2. Repository name: `tg-bot-dlya-rishuchih`, виберіть **Private** → **Create repository**.
3. На сторінці порожнього репозиторію натисніть посилання **uploading an existing file**.
4. Відкрийте папку `C:\Users\aimas\OneDrive\Desktop\TG BOT DLYA RISHUCHIH`, виділіть усе її вмістиме

### Крок 3. Створіть сервіс на Railway

1. Відкрийте **railway.com** → **Login** → **Continue with GitHub**.
2. **New Project** → **Deploy from GitHub repo**.
   Якщо репозиторію немає в списку — **Configure GitHub App** і дозвольте Railway доступ до нього.
3. Виберіть репозиторій бота. Railway сам знайде `Dockerfile` і почне збірку (2–4 хв).
4. *Лише для варіанту 2.2:* відкрийте сервіс → **Settings** → **Source**:
   **Branch** = `claude/practical-knuth-fzu8dq`, **Root Directory** = `/tg-bot-dlya-rishuchih`.
5. Перший запуск завершиться помилкою «BOT_TOKEN не задано» — так і має бути: токен додамо на наступному кроці.

> Під час збірки бот перевіряє `content.yaml`. Якщо в ньому помилка, збірка не пройде, а в журналі збірки
> (**Deployments** → **View logs** → **Build**) буде написано, у якому полі й що саме не так.

### Крок 4. Додайте токен

1. Відкрийте сервіс → вкладка **Variables** → **New Variable**.
2. Name: `BOT_TOKEN`, Value: токен із кроку 1 → **Add**.
3. Railway запропонує застосувати зміни — натисніть **Deploy** (або **Apply changes**).

Змінну `DB_PATH` **не додавайте**: бот сам знайде постійний диск.

### Крок 5. Підключіть постійний диск (Volume) — обов'язково!

Без нього після кожного оновлення чи перезапуску бот «забуде» всіх користувачів,
а повторний `/start` запустить новий 24-годинний таймер.

1. Натисніть **Ctrl+K** (на Mac — **⌘K**) і введіть `Volume` → **New Volume**
   (або клацніть **правою кнопкою** на порожньому місці полотна проєкту → **Volume**).
2. Виберіть сервіс бота.
3. **Mount Path**: `/data` → **Create**, далі застосуйте зміни (**Deploy**).
4. Після перезапуску перевірте журнал (**Deployments** → **View logs**). Має бути рядок
   `Бот @… запущено. База даних: /data/bot.db`, а попередження «…БЕЗ постійного диска…» — **ні**.

Railway не запускає дві копії сервісу з диском одночасно: під час оновлення стара копія зупиняється,
нова стартує за кілька десятків секунд. Повідомлення, надіслані боту за цей час, Telegram притримує,
і бот обробить їх після старту.

### Крок 6. Налаштуйте сервіс

Сервіс → **Settings**:

* **Restart Policy** → **Always** (бот підніметься сам після будь-якої зупинки).
  На пробному плані *Always* недоступний — лишіть **On Failure** (за замовчуванням, до 10 перезапусків).
* **Serverless** (App Sleeping) — **вимкнено** (за замовчуванням так і є). Бот має працювати постійно.
* **Replicas** — **1**. Дві копії бота з одним токеном конфліктують.
* Публічний домен (**Networking → Generate Domain**) **не потрібен**: бот сам звертається до Telegram.

### Крок 7. Перевірте, що все працює

1. **Журнал** (**Deployments** → **View logs**) після старту:
   ```
   Контент: 3 пакет(и), 4 нагадування
   Бот @dlya_rishuchyh_bot запущено. База даних: /data/bot.db
   Планувальник запущено (крок 15.0 с)
   Start polling
   ```
   Попередження «посилання-заглушка (example.com)» означає, що в `content.yaml` ще стоять приклади посилань.
2. **У Telegram**: відкрийте бота → **Start** → має прийти офер із таймером і кнопкою «Обрати пакет».
   Пройдіть: пакет → опис → «Отримати посилання на оплату».
3. **Перезапуск**: Railway → **Deployments** → ⋮ біля активного деплою → **Restart**. Через хвилину знову
   натисніть `/start` — таймер покаже **той самий** залишок часу, а не нові 24 години.

### Крок 8 (необов'язково). Сповіщення менеджеру і статистика

1. Менеджер відкриває бота, натискає **Start** (без цього бот не зможе йому писати), потім надсилає `/myid` —
   бот відповість числом.
   Для робочої групи: додайте бота в групу і надішліть у групі `/myid` → «Id цього чату: -100…».
2. Railway → **Variables**:
   * `MANAGER_CHAT_ID` = число менеджера або групи — туди приходитиме «💳 Запит посилання на оплату»
     з іменем, @username і пакетом;
   * `ADMIN_IDS` = ваш id (кілька — через кому) — вам стане доступна команда `/stats`.
3. Застосуйте зміни (**Deploy**). Railway перезапустить бота, таймери не постраждають.

## Щоденна робота

### Змінити тексти, ціни, посилання, нагадування

> **Зараз** код на Railway заливається скриптом, а не з GitHub (див. «Як розміщено зараз»): правка на GitHub
> сама не розгорнеться — попросіть Claude залити її (`python scripts/railway_deploy.py`). Нижче — як це працює,
> якщо сервіс підключено до GitHub (варіант А, крок 3).

1. GitHub → репозиторій → файл `content.yaml` → ✏️ (**Edit this file**).
2. Внесіть зміни (підказки — у коментарях у самому файлі) → **Commit changes**.
3. Railway сам збере і запустить нову версію за 2–4 хв. Таймери користувачів не скидаються.
4. Якщо в `content.yaml` помилка — збірка не пройде (у журналі збірки буде список помилок), а **попередня
   версія бота продовжить працювати**. Виправте файл і закомітьте ще раз.

Що варто знати:
* Нові тексти діють для нових повідомлень; вже надіслані повідомлення не змінюються
  (крім оферу з живим таймером — він підхопить новий текст під час наступного оновлення).
* Зміна `offer_duration` діє лише для нових користувачів.
* Не змінюйте `id` пакетів і нагадувань після запуску (див. коментарі в `content.yaml`).
* Перевірити файл на комп'ютері до коміту: `python -m bot.check_content`.

### Подивитися журнал

Railway → сервіс → **Deployments** → **View logs** (або вкладка **Logs**). Там видно запуски,
нових користувачів, надіслані нагадування, запити посилань на оплату й помилки.

### Перезапустити або зупинити

* Перезапуск: **Deployments** → ⋮ біля активного деплою → **Restart**.
* Тимчасово зупинити: **Deployments** → ⋮ біля активного деплою → **Remove**. Диск із даними лишається;
  запустити знову — **Redeploy** на останньому деплої.
* ⚠️ Не видаляйте сам **сервіс** (Settings → Delete service): разом із ним можна втратити диск із базою.

### Резервна копія бази

* Якщо на вашому плані у Volume є вкладка **Backups** — увімкніть автоматичні резервні копії за розкладом.
* Файл бази — `/data/bot.db` на диску сервісу.

## Що відбувається після перезапуску сервера

* Час першого `/start` і дедлайн кожного користувача збережені в базі — таймер іде далі, не перезапускається.
* Планувальник після старту дивиться, які нагадування вже настав час надіслати. Якщо за час простою настав час
  кількох нагадувань одразу — прийде лише найсвіжіше (без «пачки» повідомлень).
* Офер із живим таймером оновлюється з правильним залишком часу.
* Пропозиції, дедлайн яких минув під час простою, завершуються: таймер в офері → «час вийшов», кнопки зникають.

## Типові проблеми

| Що бачите | Що робити |
|---|---|
| У журналі «BOT_TOKEN не задано» | Крок 4: додайте змінну `BOT_TOKEN` |
| «Telegram не приймає BOT_TOKEN» | Токен перевипущено (`/revoke`) або скопійовано з помилкою — оновіть `BOT_TOKEN` |
| «Conflict: terminated by other getUpdates request» | Бот запущено двічі з одним токеном (наприклад, ще й на комп'ютері). Зупиніть зайву копію. Для локальних тестів створіть окремого тестового бота |
| Попередження «…БЕЗ постійного диска…» | Крок 5: підключіть Volume з Mount Path `/data` |
| Збірка зупинилась на `python -m bot.check_content` | Помилка в `content.yaml` — текст помилки в журналі збірки |
| Менеджеру не приходять сповіщення | Менеджер має спершу натиснути **Start** у боті; перевірте `MANAGER_CHAT_ID` (`/myid`) |
| Нагадування не приходять | Вони надходять лише поки пропозиція діє і лише тим, хто не заблокував бота; перевірте розклад у `content.yaml` (`python -m bot.check_content` покаже його) |
| Бот перестав працювати, план Free | Скінчився кредит — перейдіть на Hobby |

## Варіант Б — власний сервер (VPS) з Docker

Підійде будь-який VPS з **Ubuntu 24.04**, 1 vCPU і 1 ГБ RAM (Hetzner, DigitalOcean, український хостинг тощо).
Команди нижче виконуються на сервері.

1. Підключіться до сервера (у Windows — у PowerShell):
   ```bash
   ssh root@IP_СЕРВЕРА
   ```
2. Встановіть Docker:
   ```bash
   curl -fsSL https://get.docker.com | sh
   ```
3. Завантажте проєкт. Для приватного репозиторію GitHub попросить логін і замість пароля — токен доступу
   (github.com → Settings → Developer settings → Personal access tokens). Можна й просто скопіювати папку бота
   на сервер (наприклад, програмою WinSCP) і перейти в неї.
   ```bash
   git clone https://github.com/ВАШ_ЛОГІН/tg-bot-dlya-rishuchih.git bot
   ```
   ```bash
   cd bot
   ```
4. Створіть `.env` і впишіть токен (у редакторі `nano`: збереження — `Ctrl+O`, `Enter`, вихід — `Ctrl+X`):
   ```bash
   cp .env.example .env
   ```
   ```bash
   nano .env
   ```
5. Запустіть:
   ```bash
   docker compose up -d --build
   ```
6. Журнал:
   ```bash
   docker compose logs -f
   ```

* База даних лежить на томі Docker `bot-data`: вона переживає перезапуск, оновлення і перезавантаження сервера.
* `restart: unless-stopped` у `docker-compose.yml` піднімає бота після збою і після перезавантаження сервера.
* Оновити бота після зміни коду чи `content.yaml`:
  ```bash
  git pull && docker compose up -d --build
  ```
* Резервна копія бази (безпечна, навіть поки бот працює):
  ```bash
  docker compose exec bot python -c "import sqlite3; sqlite3.connect('/data/bot.db').backup(sqlite3.connect('/data/backup.db'))"
  ```
  ```bash
  docker compose cp bot:/data/backup.db ./backup.db
  ```
* ⚠️ Не виконуйте `docker compose down -v`: ключ `-v` видаляє том із базою даних.
